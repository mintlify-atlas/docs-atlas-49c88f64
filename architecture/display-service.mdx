title: 'Display Service: Framebuffer Compositor for JBD013'
description: 'How display-service drives the 640×480 JBD013 monocular display using shared memory framebuffers, dual slots, and multi-client focus management.'
---

`display-service` is a dedicated framebuffer compositor daemon that drives the JBD013 monocular display over SPI. Rather than managing rendering itself, it acts as a thin transport layer: client applications write pixel data directly into a shared memory region and then notify display-service to push that data to the panel. This Wayland/SurfaceFlinger-style split keeps the service stable even when individual client applications crash.

<Note>
`display-service` and the JBD013 display are only available in the **DisplayVersion** firmware. The AudioVersion firmware has no display hardware and does not include this service.
</Note>

## Hardware: JBD013 monocular display

| Property | Value |
| --- | --- |
| Panel | JBD013 OLED microdisplay |
| Resolution | 640 × 480 |
| Field of view | 30° monocular |
| Interface | SPI |
| Firmware variant | DisplayVersion only |

<Warning>
The camera on the reference glasses hardware is mounted at a 90° rotation. If you are rendering camera frames on the display, rotate images 90° before writing them to the framebuffer.
</Warning>

| File | Purpose |
| --- | --- |

| `jbd013_api.c` | JBD013 panel driver and SPI command layer |
| `hal_driver.c` | Hardware abstraction layer for SPI and display commands |

## Shared memory framebuffer transport

Client applications gain zero-copy display access through a POSIX shared memory region. The layout is defined by `ai_display_shm_t`:

```c
#define AI_DISPLAY_SHM_SIZE  (512 * 1024)  // 512 KB total

typedef struct {
    volatile int active_client_pid;       // PID of the client currently shown
    uint8_t framebuffer_slot_0[153600];   // Slot 0: 640 × 480 × 4 bpp
    uint8_t framebuffer_slot_1[153600];   // Slot 1: overlay / secondary app
} ai_display_shm_t;
```

The service initializes the region at startup, sets the `"DISP"` magic value, and maps it read/write. Clients map the same region, render into their assigned slot, and send a `COMMIT` message over the Unix Domain Socket at `/tmp/ai_display_service`.

### Dual slot design

Two 153,600-byte framebuffer slots support concurrent client rendering:

- **Slot 0** — main display content (primary application)
- **Slot 1** — overlay or secondary application (e.g., a notification layer)

The compositor reads whichever slot belongs to the focused client and sends it to the panel.

## Multi-client focus management

Only one client can drive the physical display at a time. Before rendering, an application must request display focus. The service grants it by recording the client's PID in `shm_ptr->active_client_pid`.

```c
// Request focus before committing frames
ai_display_request_focus(client);
```

If focus is held by another process, the commit is accepted but the frame may not be displayed until focus transfers.

## SDK API

Connect to display-service and push a frame using the following sequence:

```c
#include "ai_display.h"

int main(void) {
    // 1. Initialize the display client
    ai_display_client_t *client = ai_display_init();
    if (!client) {
        return -1;
    }

    // 2. Connect to display-service (maps shared memory)
    if (ai_display_connect(client) != 0) {
        ai_display_cleanup(client);
        return -1;
    }

    // 3. Request focus so frames are shown on the panel
    ai_display_request_focus(client);

    // 4. Get the shared framebuffer pointer and draw into it
    uint8_t *fb = ai_display_get_framebuffer(client);
    // ... render 640×480 pixels into fb ...

    // 5. Commit the frame — service reads the buffer and sends it to the panel
    ai_display_commit_frame(client, 0, 0, 640, 480);

    // 6. Clean up
    ai_display_cleanup(client);
    return 0;
}
```

To use a specific slot (for overlay rendering), use `ai_display_get_framebuffer_slot()`:

```c
// Get the overlay slot (slot 1)
uint8_t *overlay_fb = ai_display_get_framebuffer_slot(client, 1);
```

### Full display SDK reference

| Function | Description |
| --- | --- |
| `ai_display_init()` | Allocate and initialize a display client handle |
| `ai_display_connect()` | Connect to display-service and map shared memory |
| `ai_display_get_framebuffer()` | Get the primary (slot 0) framebuffer pointer |
| `ai_display_get_framebuffer_slot()` | Get the framebuffer pointer for a specific slot |
| `ai_display_request_focus()` | Request the right to drive the physical display |
| `ai_display_commit_frame()` | Notify the service to push a rendered frame to the panel |
| `ai_display_is_connected()` | Check whether the client is connected to the service |
| `ai_display_cleanup()` | Disconnect and release all client resources |
| `ai_display_get_error_string()` | Return a human-readable description of the last error |

## Power save behaviour

`display-service` includes automatic screen-off logic. After 30 seconds of inactivity (no frame commits and no GPIO events), it sends a disable command to the JBD013 panel. Any subsequent GPIO button press or frame commit wakes the display immediately.

The timeout is configurable at runtime via `AI_DISPLAY_MSG_SET_POWER_SAVE_TIMEOUT`. Set the value to `0` to disable automatic screen-off entirely.

## LVGL integration

For applications using the LVGL graphics library, configure a custom display driver whose `flush_cb` writes directly to the shared framebuffer and calls `ai_display_commit_frame()` instead of performing a memcpy:

```c
void my_flush_cb(lv_disp_drv_t *disp_drv, const lv_area_t *area, lv_color_t *color_p) {
    // Framebuffer is already the shared memory buffer — no copy needed.
    // Just notify display-service that the region is ready.
    ai_display_commit_frame(
        client,
        area->x1, area->y1,
        area->x2 - area->x1 + 1,
        area->y2 - area->y1 + 1
    );
    lv_disp_flush_ready(disp_drv);
}

// Initialize LVGL draw buffer pointing at shared memory
uint8_t *shm_buf = ai_display_get_framebuffer(client);
lv_disp_draw_buf_init(&draw_buf, shm_buf, NULL, 640 * 480);
```

The `samples/launcher-app/` directory contains a complete reference implementation of this integration pattern.
